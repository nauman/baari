baari keeps one machine-local registry of every repo you work in, and gives you a single view of what you owe a reply to — and what you're waiting on others for.

Language- and framework-agnostic. It reads conventions in your repo, not your code — the same whether a project is Rails, Go, Node, Python, or plain documentation.

macOS and Linux · no account, no network calls

v0.1.0

Today baari reads and reports — it does not write. The registry, the cross-repo view, doctor and the roster lint all work. Everything that mutates your repo, watches it, or acts on your behalf is still ahead. The direction is an opinionated framework, and the sections below mark honestly what exists and what does not.

The problem

Coordination state scatters. A note here, a thread there, a script in each project that only knows about itself.

Once you're working across several repos, there's no single place to ask the only question that matters when you sit down: what's actually waiting on me? You end up checking five directories by hand, or trusting memory.

What it does

01

baari status

Cross-repo view of what you owe a reply to, and what you're waiting on others for.

02

baari next

Just what's owed right now, across every registered repo. Nothing else.

03

baari registry

List, prune, forget, or ignore the repos baari knows about. Repos register themselves the first time you run baari inside one — there is no manual setup step.

04

baari doctor

Validate machine and repo state: registry integrity, identity, and convention markers.

05

baari thread

Inspect and scaffold coordination threads, and flag ownership assigned to names that don't exist in the owning repo.

06

baari whoami

Show the identity baari resolves for "who is me", and where it came from.

Install

Homebrew

brew install nauman/tap/baari

Without Homebrew

curl --proto '=https' --tlsv1.2 -fsSL https://nauman.github.io/baari/install.sh | sh

First run

baari identity set <your-alias>
baari status

Upgrading

baari upgrade --check   # am I behind?
baari upgrade           # do it

upgrade knows how you installed: it defers to brew upgrade for a Homebrew install rather than overwriting a managed file, and re-runs the installer otherwise. Re-running the installer by hand works too — it is the same code path, and it tells you which version it moved you from and to.

This is the only command that uses the network, and only when you run it. status, next and doctor stay offline.

Design principle

The tool will ship mechanism. Your repo will own its canon.

Nothing project-specific gets compiled into the binary — no vocabulary, no paths, no rules of ours. Every check compares a repo against itself, and thresholds come from a repo-local config file.

Not built yet. There is no config file and no --strict flag in v0.1.0 — today's commands take flags and read repo structure directly. This is the committed shape for the docs-drift checks listed as coming below, recorded here so the contract is public before the code exists.

Where the conventions come from

The binary is framework-agnostic. The practice behind it is not.

baari was extracted from a working Rails codebase and the private documentation library that governs it — a library whose written canon is heavily Rails-shaped: Ruby style and application organization, service-object and dependency-injection guidance, activity-based authorization, testing patterns, performance playbooks, Hotwire and Stimulus conventions, and a CI baseline (RuboCop omakase + performance, Brakeman, bundler-audit, importmap audit) that projects inherit rather than reinvent.

That lineage matters for one practical reason: the conventions baari reports on were pressure-tested somewhere real before they were generalised. Repo threads, roster identities, and ADR registers all earned their shape in day-to-day Rails work with CI actually gating on them.

What that does not mean: baari has no Rails-specific commands and never parses Ruby. A Go, Node, or documentation repo gets identical behaviour. Rails teams simply start further ahead, because the surrounding practice is already written down for that stack.

The docs harness

The harness is a set of home-made shell scripts. baari does not ship it yet.

The structure baari reports on — numbered plan slots, an agent roster, threads, an ADR register — is created and validated today by a handful of bash scripts: a scaffolder, a doctor that is read-only unless you pass --fix, a strict CI gate, and a slot generator. They work well and they predate the CLI.

They also live in the private repo and read its templates directly, which means they are not usable from the public binary today. Saying otherwise would be the kind of drift this whole toolchain exists to catch.

The plan, deliberately slow: scripts migrate into baari one at a time, and only when one next needs a real change — never as a big-bang rewrite. The two worth having first are the ones you would actually feel: generating a docs skeleton for a fresh repo, and a doctor that tells you where an existing tree has drifted. Those are the target; neither is in v0.1.0.

Where this is going

The goal is an opinionated framework, not a reporter that stays polite.

Stated plainly so nobody buys a roadmap as a product: none of the following is built. Some is specified in the private repo's backlog and decision records; some is intent with no spec yet. Both are labelled.

DirectionState
Thread writes — reply, park, close from the CLI specified
Docs skeleton generator — scaffold a fresh repo's docs tree intent
Docs doctor — report where an existing tree has drifted intent
Docs-drift checks — twins, generated, owners, sources specified
Repo-local config + --strict for CI specified
A watch loop with a stuck-detector specified
Listener — react to repo and CI change, notify the terminal intent
Spawn agents for review, with fallback when one is exhausted intent
Integrations and local ecosystem registries specified
Runbooks — addressable procedures with run evidence specified

specified has a written backlog item or decision record behind it. intent is a direction that has been decided but not yet specified — treat it as weaker.

What baari is not

  • Not a task manager. It reports what your repos already say, and invents no work of its own.
  • Not a service. Everything runs on your machine — no account, no sync, no telemetry. The single exception is baari upgrade, which checks for a newer release only when you run it; every other command is offline, and that is a commitment rather than a description of today's build.
  • Not a code linter. It reads repo structure and coordination files — never your source.
  • Not neutral, and not trying to be. It has opinions about how a repo should be structured, and those opinions came from somewhere specific. The plan is for local config to tune thresholds and exemptions — never to negotiate the opinion itself.
  • Not finished. See the two tables above before depending on it for anything.
