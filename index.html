Coordination

A small answer to a costly question: who owes what?

Baari reads living Markdown threads from every registered repository and presents them through one stable vocabulary. Use the human-readable output in a terminal or request bounded JSON when an agent should consume only the latest context.

01

baari status

Show work owed by you, work waiting on others, closed ownership, and parked conversations across repositories.

02

baari next

Return only the replies owed by your resolved identity.

03

baari thread list · show · lint-roster

Find conversations, read a bounded number of entries as Markdown or JSON, and catch owners missing from the repository roster.

04

baari registry

List known repositories, prune missing paths, or explicitly ignore repositories that should stay outside the cross-repo view.

Baari reads canonical threads; it does not invent a second conversation format. Thread reply, park, resume, and close commands are not part of the current release.

Delivery sequences

One registry becomes both an agent-readable plan and a beautiful human view.

A repository owns one docs/sequence.yml. Global waves describe the shared delivery order; substantial programs can add dense subwaves underneath them. Specs are assigned to those waves instead of being copied into another roadmap.

Define a global wave and a program subwave

baari docs sequence wave define W1 --title "Build"
baari docs sequence wave define W1.1 \
  --title "Commercial foundations" \
  --under W1 \
  --program commercial \
  --plan plans/commercial.md

Assign a spec, then generate global or bounded views

baari docs sequence assign specs/031-capabilities.md --to W1.1
baari docs sequence build
baari docs sequence build \
  --program commercial \
  --output docs/plans/commercial/00-delivery-sequence

The default build writes docs/plans/00-delivery-sequence.md and docs/plans/00-delivery-sequence.html. A program filter keeps its parent and dependency context and requires an explicit output path. Every result is a projection; sequence.yml remains the source.

Documentation and guardrails

Scaffold the convention once. Then make drift visible.

01

baari docs init · docs doctor

Create the canonical docs tree from embedded templates, then report structural drift. Add --strict when findings should fail CI.

02

baari adr list · adr check

Read the decision register and catch malformed records, invalid status values, or index drift.

03

baari ci tree

Show which repository guard layers are present, unwired, or absent. Stable JSON and strict exit behavior make it usable in automation.

04

baari explain

Explain the delivery model from workbench and requirements through architecture, specs, sequence, and status.

05

baari contract

Emit the versioned JSON command ledger that drives the virtual terminal above and travels with every release.

Safe local work

Shared checkouts need explicit boundaries, not optimistic cleanup.

01

baari worktree list · prune

Inspect every checkout and remove only worktrees where nothing would be lost. Pruning is a dry run until --confirm.

02

baari testdb list · prepare · prune

Give each checkout its own test database, prepare the current one, and identify databases whose worktree no longer exists.

03

baari doctor

Validate the machine registry, resolved identity, repository markers, and roster before work starts.

Behavior you can reason about

Local-first does not mean pretending every command is read-only.

BehaviorCommandsBoundary
Read status, next, whoami, doctor, contract, thread reads, docs doctor, ADR checks, CI tree Read local repository and machine state.
Local state identity, registry, thread scaffold Write explicit configuration or scaffolding under your user-owned Baari state.
Repository docs init, sequence wave/assign/build Write named documentation artifacts. Existing docs are replaced only when the command explicitly allows it.
Workspace worktree prune, testdb prepare, testdb prune Potentially mutating operations are explicit; prune commands preview before confirmation.
Network upgrade, optional auth Upgrade checks releases. Auth delegates access checks and sync to your authenticated GitHub CLI.

There is no Baari account, cloud workspace, telemetry client, listener, or resident process in the current release. Normal coordination and documentation checks run against files already on your machine.

Optional authenticated canon

Teams can layer private guidance on top of the embedded generic rules.

A repository may name an additional documentation source in .baari.yml. baari auth status, auth init, and auth sync use the existing gh login; Baari stores no GitHub token. Without access, the embedded generic set remains available.
